#### Skidpad
Delaunay is not capable to solve the skidpad problem.
The event map is hardly constraint by the rules so is more of a fitting problem rather than a trajectory problem.
What could be done???
- Define the skidpad map through global points
- Run ICP (Iterative Closest Point) to fit the known map into the environment
- Adjust the known trajectory segment with the real measurement of the car after the ICP
- Feed everything to the control node
- Check if i passed a gateway to change the state of the state-machine

  - RIGHT_LAP_2
  - LEFT_LAP_1
  - LEFT_LAP_2
  - EXIT_AND_STOP

#### Track limits
Delaunay is very good if you assume to always have a decent amount of data to work with.
What happens in case of a missing track side??? What happens if you see few cones on one side and a lot on the other???
Getting rid of Delaunay could be helpful if only the spline calculation is used.
What is the new procedure that has to be tried out???
- Separate the cones into the two sides
- Order each side respect to the car
- Connect the side with a spline and sample it every X meters (both sides)
- Calculate the middle point with L[i] and R[j] where i == j
- If the sizes do not match, for the longer side, calculate the normal vector for the unpaired points and move them towards the center of the track
- Pass the new array of midpoints to the spline to obtain the path to follow
- Extend the trajectory if needed or required

#### Replace the depth map
Using the depth map of the Zed2i highly relies on the GPU capabilities. Slower GPUs worse performances.
Calculating the depth map each frame is expensive on computations so every node could be affected performance talking.
Maybe there is a better way to extrapolate the depth of a cone without using the depth map generated by the AI model of Stereolabs.
